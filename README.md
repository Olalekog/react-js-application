# AWS Multi-Account 3-Tier Application - Secure No-Cognito Local Authentication

This project deploys a secure, scalable, multi-account AWS 3-tier application using **Terraform**, **GitHub Actions**, **Docker**, **EC2 Auto Scaling Groups**, **Application Load Balancers**, **Amazon RDS MySQL**, **ACM**, **Route 53**, **AWS Secrets Manager**, **SSM Parameter Store**, and **KMS encryption**.

This version **does not use Amazon Cognito**. Authentication is handled directly by the application backend using local username/password accounts stored in Amazon RDS MySQL.

The application has:

- **Frontend:** React.js packaged as a Docker image and served by Nginx
- **Backend:** Python FastAPI packaged as a Docker image
- **Database:** Amazon RDS MySQL with RDS-managed password stored in AWS Secrets Manager
- **Authentication:** Local username/password registration and login handled by FastAPI
- **Security:** HTTPS with ACM, Route 53 DNS, JWT authentication, bcrypt password hashing, KMS encryption
- **Infrastructure:** Terraform modules deployed through GitHub Actions
- **Account model:** Tooling, Dev, UAT, and Production AWS accounts

## ACM HTTPS Design

The project uses **AWS Certificate Manager** to secure the public Application Load Balancer with HTTPS.

Terraform creates:

- ACM certificate for the environment DNS name
- Route 53 DNS validation records
- HTTPS listener on ALB port `443`
- HTTP listener on ALB port `80` that redirects to HTTPS
- TLS security policy on the ALB listener

Traffic flow:

```text
User Browser
  |
  | HTTPS 443
  v
Route 53 alias record
  |
  v
Public ALB with ACM certificate
  |
  v
Frontend EC2 ASG
```

HTTP traffic is redirected:

```text
http://app.dev.mydevopsprojects.shop
  |
  v
301 redirect
  |
  v
https://app.dev.mydevopsprojects.shop
```

## Authentication Design - No Cognito

This project intentionally does **not** use Amazon Cognito.

Users create and sign in with a local account managed by the FastAPI backend.

```text
User Browser
  |
  v
React Login/Register Form
  |
  | POST /api/auth/register
  | POST /api/auth/login
  v
FastAPI Backend
  |
  | Hashes passwords with bcrypt
  | Stores users in RDS MySQL
  | Issues application JWT
  v
Amazon RDS MySQL
```

FastAPI protects API routes using JWT bearer tokens:

```http
Authorization: Bearer <application-jwt>
```

The JWT signing secret is generated by Terraform and stored in AWS Secrets Manager using KMS encryption.

### Authentication Endpoints

```text
POST /api/auth/register
POST /api/auth/login
GET  /api/auth/me
```

### Register Example

```bash
curl -X POST https://app.dev.mydevopsprojects.shop/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"John Doe","email":"john@example.com","password":"StrongPassword123!"}'
```

### Login Example

```bash
curl -X POST https://app.dev.mydevopsprojects.shop/api/auth/login \
  -H "Content-Type: application/json" \

```

### User Table

The backend creates this table if it does not already exist:

```sql
CREATE TABLE IF NOT EXISTS users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

## Application Architecture

The application follows a 3-tier design.

### 1. Presentation Tier

The presentation tier runs the React.js frontend.

It is deployed as a Docker container on EC2 instances inside an Auto Scaling Group. Nginx serves the React static files and proxies API requests to the backend through the internal Application Load Balancer.

Main components:

- React.js
- Nginx
- Docker
- EC2 Auto Scaling Group
- Public Application Load Balancer
- Route 53 public DNS
- ACM HTTPS certificate

### 2. Application Tier

The application tier runs the Python FastAPI backend.

It is deployed as a Docker container on EC2 instances inside a separate Auto Scaling Group. The backend is private and is only reachable through the internal Application Load Balancer.

Main components:

- Python FastAPI
- Gunicorn/Uvicorn
- Docker
- EC2 Auto Scaling Group
- Internal Application Load Balancer
- IAM instance role
- AWS Secrets Manager integration
- bcrypt password hashing
- JWT authentication

### 3. Database Tier

The database tier uses Amazon RDS for MySQL.

The database is deployed in private database subnets and is not publicly accessible. RDS generates and manages the master password in AWS Secrets Manager.

Main components:

- Amazon RDS MySQL
- Private DB subnet group
- RDS-managed Secrets Manager password
- KMS encryption
- Automated backups
- Multi-AZ support for production

## Request Flow

When a user submits data from the frontend, the request follows this path:

```text
User Browser
  |
  | HTTPS
  v
Route 53
  |
  v
Public Application Load Balancer
  |
  v
Frontend EC2 ASG
React.js + Nginx container
  |
  | /api/* request proxy
  v
Internal Application Load Balancer
  |
  v
Backend EC2 ASG
FastAPI container
  |
  | reads database secret and JWT secret from AWS Secrets Manager
  v
Amazon RDS MySQL
```

The frontend never connects directly to the database. All database reads and writes go through the backend API.

---

## Database Write Flow

When the frontend adds or registers a user:

1. User enters data in the React form.
2. React sends a request to the backend API.
3. Nginx proxies the request to the internal backend ALB.
4. FastAPI validates the request using Pydantic.
5. FastAPI reads secrets from AWS Secrets Manager.
6. FastAPI hashes the password if it is a registration request.
7. FastAPI connects to RDS MySQL.
8. FastAPI inserts or reads records from the `users` table.
9. FastAPI returns a success response and JWT token where applicable.

---

## FastAPI Startup Database Initialization

The backend initializes the database table during application startup.

This is useful for dev and learning environments. For production, a dedicated migration tool such as Alembic or Flyway is recommended.

The backend creates the `users` table if it does not already exist.

Availability Zones are selected dynamically with Terraform:

```hcl
data "aws_availability_zones" "available" {
  state = "available"
}

locals {
  selected_availability_zones = slice(data.aws_availability_zones.available.names, 0, var.az_count)
}
```

Each environment creates:

```text
1 VPC
3 dynamically selected Availability Zones
3 public subnets
3 private frontend subnets
3 private backend subnets
3 private database subnets
Internet Gateway
NAT Gateways
Public route table
Private route tables
Database subnet routing
```

## GitHub Actions Workflows

### 1. Tooling Foundation Workflow

File:

```text
.github/workflows/tooling-foundation.yml
```

Purpose:

Creates the central tooling foundation.

Creates:

- S3 bucket for Terraform remote state
- DynamoDB table for Terraform state locking
- KMS key for state encryption
- GitHub OIDC provider
- GitHub bootstrap role

This workflow runs first.

### 2. Bootstrap Multi-Account Workflow

File:

```text
.github/workflows/bootstrap-multi-account.yml
```

Purpose:

Creates required resources in dev, uat, and production accounts.

Creates:

- Dev deploy role
- UAT deploy role
- Production deploy role
- ECR repositories in each target account
- SSM SecureString parameters in the tooling account

### 3. App Deploy Workflow

File:

```text
.github/workflows/app-deploy.yml
```

Purpose:

Builds and deploys the application.

The workflow:

1. Resolves environment based on branch.
2. Assumes the tooling bootstrap role using GitHub OIDC.
3. Reads the target account deploy role ARN from SSM SecureString.
4. Assumes the target account deploy role.
5. Builds Docker images.
6. Pushes Docker images to ECR in the target account.
7. Runs Terraform using centralized state.
8. Deploys or updates the environment stack.
9. Requires approval before production apply.

## Security Design

This project uses multiple security controls:

- GitHub OIDC instead of long-lived AWS keys after tooling bootstrap
- Centralized Terraform state encrypted with KMS
- DynamoDB state locking
- SSM SecureString for deploy role ARN parameters
- Least-privilege deploy roles per environment
- Environment-specific AWS accounts
- Terraform-created VPCs per environment
- Dynamic Availability Zone selection
- Private EC2 instances
- Private RDS database
- RDS-generated password stored in AWS Secrets Manager
- Application JWT secret stored in AWS Secrets Manager
- bcrypt password hashing
- HTTPS with ACM certificates
- HTTP to HTTPS redirect
- Route 53 alias records
- KMS encryption for RDS, EBS, ECR, logs, SSM, Secrets Manager, and state
- Security groups allowing only required traffic flows
- Production approval gate in GitHub Environments

## Secrets Management

The database password is not stored in GitHub and is not passed as a Terraform variable.

RDS creates and manages the master password in Secrets Manager using:

```hcl
manage_master_user_password   = true
master_user_secret_kms_key_id = var.kms_key_arn
```

The backend receives these environment variables:

```text
DB_SECRET_ARN
APP_JWT_SECRET_ARN
AWS_REGION
```

The backend EC2 instance role has permission to call:

```text
secretsmanager:GetSecretValue
kms:Decrypt
```

## Operational Notes

- Run tooling first.
- Run bootstrap second.
- Deploy dev before uat.
- Deploy uat before production.
- Keep production protected with approval gates.
- Do not store database passwords in GitHub.
- Do not store JWT secrets in GitHub.
- Do not allow SSH from the internet.
- Use SSM Session Manager for EC2 access.
- Use immutable image tags based on Git SHA.
- Use separate AWS accounts for environment isolation.
- Use HTTPS for all public access.
- Keep the backend and database private.

## Final Summary

This project implements a secure AWS multi-account 3-tier application deployment platform. The tooling account provides centralized CI/CD trust and Terraform state. The bootstrap stack prepares each target account with deploy roles and ECR repositories. The app stack deploys the React frontend, FastAPI backend, and RDS MySQL database into dev, uat, and production accounts using reusable Terraform modules and GitHub Actions automation.

The application is secured with Route 53 DNS, ACM HTTPS certificates, private networking, Secrets Manager, KMS encryption, and local application-managed username/password authentication. Cognito, Google login, and Facebook login are intentionally not used in this version.
